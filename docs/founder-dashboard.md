# Founder workspace: setup and security

The founder workspace is a **separate authorization**, not a synonym for the existing Super Administrator role. No account is enrolled automatically by the migration, `createsuperuser`, public registration, Google Sign-In, or the demo seed. The earlier Super Administration overview is replaced: an enrolled founder is directed to `/founder/`; another super-administrator keeps the ordinary operations dashboard and their existing permissions. This change does **not** remove or promote accounts.

The new workspace is read-only for business data. Its password + TOTP step-up, session state, sign-in events and audit records do write their own security/activity records. Account support deliberately shows metadata only: private PDF contents, question/answer text, scores, private filenames, class codes, passwords, OTPs and card data are not displayed or opened. A separate consent-based private-content support workflow has **not** been implemented.

## Before upgrading any real installation

1. Verify the target environment and branch. Back up the database **and** private files, verify the backup can be restored, and schedule maintenance. Do not replace an existing database, media folder, private files, `.env`, or user accounts with files from a clone or sandbox.
2. Install the updated `requirements.txt`, check `python manage.py migrate --plan`, apply `python manage.py migrate` to the correct database, run `python manage.py collectstatic --noinput` when using production static files, and restart the web and worker processes. The founder migration adds its own tables and a tracking-start marker; it does not backfill login events or change accounts, purchases, attempts, answers or timers. Rehearse with isolated synthetic data first, and test backup restoration only in a controlled recovery environment authorized to handle those private records.
3. The live public website and founder page should use the **same production application/database and protected storage**. Development/staging must use separate databases, private-file roots, configuration, accounts, secrets and provider credentials. Never enable `ALLOW_TEST_PAYMENT_CREDITS` against production data. A separate founder subdomain is optional future infrastructure, not required by this implementation.
4. In production use `DEBUG=False`, unique strong `SECRET_KEY`, secure session and CSRF cookies, valid HTTPS and correctly configured hostnames/origins. `/founder/` refuses insecure HTTP when `DEBUG=False`. Configure `TRUST_PROXY_HTTPS=True` only when your trusted reverse proxy strips client-supplied forwarding headers and supplies the actual scheme. Restrict access further with a VPN or proxy/network allowlist and use a WAF/rate limiting on the **normal login** too. The founder step-up rate limit does not rate-limit other login or administration endpoints. Have qualified personnel independently review the deployment and restore plan before exposing real data.
5. **Do not run `seed_admin` on a real installation.** Its published demo passwords are predictable, and the command now refuses to run with `DEBUG=False`. This does not remove or secure demo accounts that might already exist. Identify and secure or disable any such existing accounts without deleting protected records. Do not rely on the `DEBUG=False` guard if a deployment is misconfigured with debug enabled.

## Explicitly enroll the one intended founder

Only an existing active account with the stored `SUPER_ADMIN` role, a usable password and no pending email-verification requirement can be enrolled. An inconsistent student, teacher or ordinary admin row is ineligible even if its Django `is_superuser` flag is set. A `SUPER_ADMIN`-role account need not have that separate flag. Decide the exact account yourself; do not infer founder status from a name in a registrations list. Use a strong, unique account password; normal password login and the new authenticator factor are both required. Enrollment does not change the account's role, staff flag, superuser flag, or password.

1. Generate a **separate, random Fernet key** on the target server, for example:

   ```text
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```

   Put the output in that environment's protected secret manager or private `.env` as `FOUNDER_TOTP_ENCRYPTION_KEY`. It must differ from `SECRET_KEY`, every `SECRET_KEY_FALLBACKS` value, and keys in other environments; reuse of a Django signing key is rejected. Restart the application so all web workers have the same key. Do not put it in Git, terminal recordings, tickets or chat. An empty, malformed or wrong key makes the founder area unavailable; there is no default key.
2. In a trusted server terminal, after checking the username and database, run:

   ```text
   python manage.py founder_access grant --username EXACT_EXISTING_USERNAME --confirm
   ```

   The command prints a new authenticator setup secret **once**. Treat the terminal output like a password: do not capture it in logs, screenshots or chat. Enter it manually into a time-based authenticator app (six digits, 30-second period). The server stores the seed encrypted with the separate Fernet key. The command refuses to overwrite an already enabled founder.
3. Sign in normally at `/auth/login/`, open `/founder/`, then enter the account password and a fresh authenticator code. The successful founder session lasts at most 15 minutes. Accepted TOTP time steps cannot be reused across browsers; wait for the next code when unlocking again. Five unsuccessful checks lock founder verification for 15 minutes across workers. The lock is not a global login lockout. The server clock must be synchronized; one adjacent 30-second TOTP step is allowed for clock drift.
4. Use **Lock** to close the founder session without changing the normal site login. Normal logout also closes it. These controls protect the founder pages only; they do **not** add 2FA to existing Django admin, the ordinary operations dashboard, or other services. Existing Django-superuser billing and role-management permissions remain as before and must be secured separately.

To revoke access immediately without changing the account:

```text
python manage.py founder_access revoke --username EXACT_EXISTING_USERNAME --confirm
```

Revocation does not require the encryption key and invalidates unlocked sessions on their next request; it cannot cancel a response that already passed authorization and is in progress. To replace a lost authenticator, revoke and then grant again in a trusted terminal. There are no recovery codes or self-service reset. If the encryption key is lost or replaced, existing seeds cannot be recovered without its protected backup; revoke and re-enroll **each** affected founder under the replacement key. Back up the key separately from the database, limit operator access, and test your recovery procedure. CLI grant/revoke events are attributed to “System”; use separately protected host/operator logs to identify the human operator.

## What the numbers mean

- **Registered students/teachers** are accounts in those current roles. “Enabled” means `is_active`; it does not mean online. JEE/NEET counts use the explicit current student track. Unclassified legacy accounts are not guessed.
- **Recorded sign-ins** come from successful Django sign-in events after the migration's start marker, including automatic sign-in after registration. They are unique people separately from total sign-in events. If an account is deleted, its anonymized event remains in the event count but cannot be included among identifiable unique people. The daily table marks earlier untracked days as unavailable rather than zero and marks the first tracking day as partial. The previous `last_login` value remains visible as a single timestamp, not a reconstructed history. Logging failures are reported to server logs and do not block ordinary sign-ins; interruptions can create gaps. These counts are not unique website visitors or people currently online. Dates are displayed in the configured Asia/Kolkata timezone.
- **Attempts** include private practice, classroom, series and other/institutional types as separate categories. The “in progress” database status can include an overdue attempt until its existing expiry processing runs; it is not an online count. Account support displays the original recorded expiry without changing it.
- **Payments** combine recorded pack and legacy plan payments. Distinct payers are deduplicated across both systems, including people whose captured payment was later refunded. Counts exclude failed payments from captures; INR sums exclude other currencies, and non-INR table amounts are shown in recorded minor units without assuming their decimal scale. Refund totals only sum refund rows actually recorded. Provider-reported refund status can precede those rows, so no net revenue is invented. Payment tables have no per-record mode field; the currently implemented gateways are test-only, and imported or altered data needs independent verification. No real-money revenue or live activation is claimed. Verify reconciliation, KYC, production implementation and actual provider behavior before any approved live launch.
- **Series** report assigned slots and the existing readiness checks for content, track, private assets and confirmed keys. A missing slot is not an invented test. The first of 16 is free, then ₹299 for the other 15. New PDF packs are ₹299/20 after the first free PDF; student classroom packs ₹99/20 after the first free classroom start; teacher packs ₹299/20 after the first free 24-hour activation. New pack credits do not expire; historical plans may have different terms. Forty students is not a cap.
- **Alerts** are database flags needing review, not confirmed incidents. Exam browser signals are not proof of cheating. Audit and sign-in history contain only events actually recorded; audit records are not tamper-proof. Historical audit descriptions can contain filenames, titles or scores, so the founder workspace shows their event metadata while withholding their free text; only strictly matched, safe founder-action details are displayed. Original logs are not changed. Use independently protected, centralized append-only security logs, monitoring, retention, access review and alerts in a real deployment. Do not record founder form bodies, authenticator secrets or raw private search terms in reverse-proxy logs.

The founder security controls are application-level defenses, not a guarantee of safety against a compromised operator, server, database, encryption key, browser, existing privileged role or vulnerable dependency. Review all remaining privileged endpoints, backups, infrastructure and incident-response procedures before production.
